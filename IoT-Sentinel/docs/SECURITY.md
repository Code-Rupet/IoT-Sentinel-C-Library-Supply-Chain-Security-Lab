# Cybersecurity Analysis & Threat Model — IoT Sentinel

This document provides a university-grade cybersecurity analysis of the **IoT Sentinel** system. It evaluates the architectural trust boundaries, hardware attack surfaces, cryptographic controls, network traffic profile, and supply-chain considerations.

---

## 1. Threat Modeling & Trust Boundaries

The system spans three distinct trust domains:

1. **Edge Domain (ESP32 Microcontroller)**: Operating in an untrusted or semi-trusted physical environment (e.g., student lab or field deployment). Susceptible to physical tampering, bus snooping, and memory extraction.
2. **Transit Domain (Public Internet)**: Untrusted WAN. Subject to packet eavesdropping, DNS spoofing, man-in-the-middle (MitM) interception, and denial-of-service (DoS) attempts.
3. **Cloud Domain (Google Apps Script & Drive)**: Trusted SaaS/serverless infrastructure. Manages persistent file storage, user authorization, and execution sandboxing.

```
+-----------------------------+           +--------------------------+           +------------------------------+
|     EDGE TRUST DOMAIN       |   HTTPS   |   TRANSIT TRUST DOMAIN   |   HTTPS   |      CLOUD TRUST DOMAIN      |
|  [ESP32 Microcontroller]    | =========>|   [Public Internet]      | =========>|  [Google Apps Script/Drive]  |
|  - GPIO 2 / Hardware State  | (TLS 1.3) |  - DNS Eavesdropping     | (TLS 1.3) |  - Isolated V8 Execution     |
|  - SRAM / SPI Flash Secrets |           |  - Active MitM Threats   |           |  - Encrypted Script Props    |
+-----------------------------+           +--------------------------+           +------------------------------+
```

## 2. Cryptographic Validation & TLS Architecture

### Root of Trust & Certificate Validation
A major vulnerability in educational embedded projects is disabling TLS verification via `WiFiClientSecure::setInsecure()`. This renders HTTPS indistinguishable from plaintext against an adversary capable of ARP spoofing or DNS poisoning.

* **IoT Sentinel Implementation**: The firmware strictly enforces root CA validation by embedding the **Google Trust Services (GTS) Root R1** certificate (RSA 4096-bit, SHA-384, expiring in 2036).
* **Certificate Authority Anchor**:
  - Subject: `C=US, O=Google Trust Services LLC, CN=GTS Root R1`
  - Serial: `02:03:e5:93:6f:31:b0:13:49:88:6b:a2:17`
  - Fingerprint (SHA-256): `d9:47:43:2a:bd:e7:b7:fa:90:fc:2e:6b:59:10:1b:12:80:e0:e1:c7:e4:e4:0f:a3:c6:88:7f:ff:57:a7:f4:cf`

### Network Time Protocol (NTP) Dependency
X.509 certificate validation requires knowing the current time to verify that the certificate is within its `notBefore` and `notAfter` validity window. Embedded microcontrollers lack a battery-backed Real-Time Clock (RTC).
* If time is uninitialized (epoch 0 = Jan 1, 1970), mbedTLS rejects valid modern certificates with `MBEDTLS_ERR_X509_CERT_VERIFY_FAILED` (flag: `MBEDTLS_X509_BADCERT_FUTURE` or `BADCERT_EXPIRED`).
* **Control**: `WiFiManager::syncTime()` queries authenticated NTP servers (`pool.ntp.org` / `time.google.com`) and verifies the system clock has advanced past **January 1, 2024** before allowing TLS handshakes.

## 3. Authentication Analysis & Shared Token Limitations

The receiver authenticates requests via a shared alphanumeric token (`DEVICE_TOKEN`).

### Strengths
1. Prevents arbitrary unauthorized third parties from polluting the Google Drive storage folder.
2. Verified in Google Apps Script using `constantTimeEquals()` to protect against timing attacks.
3. Automatically stripped from the payload prior to saving the JSON file in Drive (preventing token sprawl across Drive search indexes).

### Limitations (The Embedded Secret Problem)
1. **Extraction via Flash Dump**: On standard ESP32 boards without hardware flash encryption, an attacker with brief physical access can attach a USB cable, invoke `esptool.py read_flash 0x0 0x400000 dump.bin`, and run `strings dump.bin | grep sentinel_` to extract `SECRET_DEVICE_TOKEN` and Wi-Fi credentials in seconds.
2. **Replay Attacks**: Because the pre-shared token is static, an attacker capable of compromising TLS termination (e.g. via compromised CA or endpoint proxy) can replay captured payloads.

### Production Countermeasures (Enterprise Recommendations)
* **Secure Elements**: Interface a cryptographic coprocessor (such as the Microchip ATECC608A or OPTIGA Trust M) over I2C to store private keys and sign requests via asymmetric ECDSA tokens (JWTs).
* **ESP32 Hardware Security**: Enable **ESP32 Flash Encryption** (AES-256-XTS) and **Secure Boot v2** (RSA-3072 signature validation) via the eFuse controller.

## 4. Expected vs. Observed Network Destinations (Wireshark Profile)

All network traffic generated by IoT Sentinel is documented, intentional, and strictly confined:

| Protocol | Destination Port | Host / IP Range | Operational Purpose |
| :--- | :--- | :--- | :--- |
| **DHCP** | UDP 67/68 | Local Gateway (`255.255.255.255`) | IPv4 address allocation and DNS server assignment. |
| **DNS** | UDP 53 | Configured Gateway / ISP DNS | Resolves NTP and Google domain hostnames. |
| **NTP** | UDP 123 | `pool.ntp.org`, `time.google.com` | Synchronizes system clock for X.509 certificate validation. |
| **HTTPS**| TCP 443 | `script.google.com` (Google Front End) | Submits initial POST telemetry payload with token. |
| **HTTPS**| TCP 443 | `script.googleusercontent.com` (Google CDN) | Follows safe 302 redirect to retrieve execution confirmation. |

### Wireshark Verification Procedure
To verify that no covert, third-party, or unexpected connections are established:
1. Connect your computer to the same Wi-Fi Access Point as the ESP32.
2. Configure your Wi-Fi interface in monitor mode or connect through an Ethernet bridge / software AP (e.g. using `hostapd` or mobile hotspot).
3. Start Wireshark with the display filter:
   ```wireshark
   ip.addr == <ESP32_IP_ADDRESS>
   ```
4. Observe the traffic sequence:
   - Initial DHCP exchange (`bootp`).
   - NTP queries (`ntp`).
   - TLS Client Hello to Google IP ranges (`tls`).
   - **Zero** outbound connections to unknown IP addresses or unencrypted HTTP (TCP 80).

## 5. Software Supply-Chain & Dependency Management

### Dependency Inventory
IoT Sentinel intentionally minimizes dependencies to reduce attack surface:

| Library | Author | Scope | Pinned Baseline |
| :--- | :--- | :--- | :--- |
| **ArduinoJson** | Benoit Blanchon | Core JSON serializer | `^7.0.0` or `^6.21.0` |
| **WiFi** | Espressif Systems | Core ESP32 SDK | Included in ESP32 Core `v3.0.x` |
| **WiFiClientSecure** | Espressif Systems / mbedTLS | Core TLS engine | Included in ESP32 Core `v3.0.x` |
| **HTTPClient** | Espressif Systems | HTTP protocol parser | Included in ESP32 Core `v3.0.x` |

### Supply-Chain Risk Simulation: Compromised Dependency
What happens if a rogue contributor injects malicious code into a third-party dependency?
* **Demonstration Attack Vector**: A compromised library could intercept the `serializeJson()` call, inject an extra JSON key (e.g. `exfil_data: [wifi_password]`), or spawn a background thread connecting to a command-and-control (C2) server.
* **Defensive Controls Built into IoT Sentinel**:
  1. **Strict Cloud Schema Allowlist**: Even if a compromised library injected unauthorized fields, Google Apps Script rejects any payload violating the strict schema or attempts to write unverified fields.
  2. **Domain-Restricted Transport**: `GoogleDriveClient::isSafeGoogleRedirect` strictly drops redirects pointing to any host outside `*.google.com` and `*.googleusercontent.com`.
  3. **Zero Secret Printing**: No credentials or raw memory are printed to the console.

## 6. Firmware Integrity & Binary Hashing

To ensure the compiled binary uploaded to the ESP32 has not been tampered with or modified after build:

1. Generate the SHA-256 cryptographic hash of the compiled `.bin` file:
   ```bash
   sha256sum build/esp32.esp32.esp32/IoTSentinel.ino.bin
   ```
2. Record the resulting digest in the lab notebook or deployment log (e.g., `8f7b3c2...`).
3. If investigating a potentially compromised device, read back the flash memory and compare the hash:
   ```bash
   esptool.py --port /dev/ttyUSB0 read_flash 0x10000 0x180000 extracted_firmware.bin
   sha256sum extracted_firmware.bin
   ```

## 7. Data Minimization & Privacy

IoT Sentinel strictly adheres to privacy by design (GDPR Article 25 & IoT Security best practices):
- **Collected Metrics**: Device ID, Event Type, Firmware Version, Uptime, Wi-Fi Connection Boolean, Wi-Fi RSSI (dBm), LED Hardware State ("ON"/"OFF").
- **Exclusion List**: The device **never** collects:
  - MAC addresses of nearby routers or devices (no Wi-Fi promiscuous sniffing).
  - Internal network host scans or IP tables.
  - Personal identifiable information (PII) or host files.
  - Plaintext authentication secrets in Drive output files.
